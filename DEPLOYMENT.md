## 1. Что потребуется

**Сервер.** Linux, 2 ГБ оперативной памяти, 20 ГБ диска. Этого хватает с
запасом: одна станция при интервале замера 60 секунд даёт примерно
1,5 млн записей в год, то есть около 300 МБ вместе с индексами.

**Доступ.** Root или пользователь в группе `docker`.

**Сеть.** Снаружи должны быть открыты порты 80, 443 и 1883. Последний
нужен станции, чтобы подключиться к брокеру. Домен должен указывать на
сервер ещё до первого запуска, иначе Let's Encrypt не выпустит
сертификат. Исходящий интернет нужен для скачивания образов и,
по желанию, для определения городов по координатам.

**Для прошивки.** Компьютер с Arduino IDE и кабель micro-USB.

Состав проекта:

```
firmware/            прошивка ESP32 + INSTRUCTIONS.md (распиновка, библиотеки, ошибки)
mosquitto/           конфигурация брокера MQTT
backend/             FastAPI + SQLAlchemy async + PostgreSQL
frontend/            Svelte 5 + Vite, панель управления
docker-compose.yml   профили prod и dev
Caddyfile            внешний реверс-прокси и TLS
.env.example         шаблон переменных окружения
```

## 2. Подготовка сервера

### Docker

```bash
curl -fsSL https://get.docker.com | sh
```

Убедитесь, что встал плагин compose второй версии. В проекте
используются профили, а старый `docker-compose` с дефисом их не знает:

```bash
docker compose version
```

Ожидается `v2.x` или новее.

### Распаковка проекта

```bash
mkdir -p /opt/envmon && cd /opt/envmon
unzip ~/env-monitoring.zip
```

### Файрвол

```bash
ufw allow 22/tcp
ufw allow 80/tcp
ufw allow 443/tcp
ufw allow 1883/tcp
ufw enable
```

Порт PostgreSQL наружу открывать не нужно, в профиле `prod` база живёт
только во внутренней сети Docker.

Насчёт 1883: брокер слушает без TLS, но анонимный доступ закрыт, пароль
обязателен и для станции, и для сервера. Если станция и сервер стоят в
разных сетях и открытый канал вас не устраивает, поднимайте между ними
VPN. Можно вместо этого добавить в `mosquitto/mosquitto.conf` второй
listener на 8883 с сертификатом, но тогда прошивку придётся переводить
на `WiFiClientSecure` с вшитым корневым сертификатом, а его нужно
обновлять раз в несколько месяцев. На автономной станции VPN обычно
проще.

## 3. Переменные окружения

```bash
cp .env.example .env
```

Секреты лучше сгенерировать, а не придумывать:

```bash
openssl rand -hex 32     # JWT_SECRET
openssl rand -hex 24     # DEVICE_TOKEN
openssl rand -hex 16     # POSTGRES_PASSWORD и MQTT_PASSWORD
```

Что заполнять в `.env`:

| Переменная | Что указать |
|---|---|
| `SITE_ADDRESS` | Домен, например `monitor.example.com`. Для запуска по IP без TLS оставьте `:80` |
| `POSTGRES_PASSWORD` | Сгенерированная строка |
| `JWT_SECRET` | Сгенерированная строка |
| `ADMIN_EMAIL` | Логин первого аккаунта панели |
| `ADMIN_PASSWORD` | Пароль, минимум 8 символов |
| `DEVICE_ID` | Идентификатор станции, например `station-01` |
| `DEVICE_NAME` | Отображаемое имя, например `Река Кама, пост 1` |
| `MQTT_USER` | Логин станции на брокере, например `station` |
| `MQTT_PASSWORD` | Сгенерированная строка, её же вписать в прошивку |
| `DEVICE_TOKEN` | Нужен только резервному HTTP-приёму |
| `GEOCODE_ENABLED` | `true`, если у сервера есть интернет и нужны названия городов |

Пять переменных обязательны: `POSTGRES_PASSWORD`, `JWT_SECRET`,
`ADMIN_PASSWORD`, `DEVICE_TOKEN`, `MQTT_PASSWORD`. Если оставить их
пустыми, compose откажется стартовать. Так сделано специально, чтобы
система не уехала в продакшен с паролем из примера.

```bash
chmod 600 .env
```

Значения `DEVICE_ID`, `MQTT_USER` и `MQTT_PASSWORD` понадобятся на
шестом шаге, выпишите их куда-нибудь.

## 4. Запуск в продакшене

```bash
docker compose --profile prod up -d --build
```

Первая сборка занимает 3–5 минут, собираются образы Python и Node.
Поднимаются пять контейнеров:

| Контейнер | Роль |
|---|---|
| `db` | PostgreSQL 16, данные в томе `pgdata` |
| `mosquitto` | Брокер MQTT, порт 1883 наружу для станции |
| `api` | FastAPI с мостом MQTT внутри, 2 воркера uvicorn |
| `web` | Собранная статика панели под внутренним Caddy |
| `caddy` | Внешний прокси и TLS, единственная точка входа для браузера |

Файл паролей брокера создаётся заново при каждом старте контейнера из
`MQTT_USER` и `MQTT_PASSWORD`. Сам пароль живёт только в `.env`, ни в
образ, ни в репозиторий он не попадает.

Проверить состояние:

```bash
docker compose --profile prod ps
docker compose --profile prod logs -f api
```

При первом старте в логах `api` должны появиться строки о создании
первого пользователя и регистрации станции. Схема БД создаётся
автоматически, миграции запускать не нужно.

Если в `SITE_ADDRESS` домен, Caddy получит сертификат в течение минуты.
За этим можно следить:

```bash
docker compose --profile prod logs -f caddy
```

## 5. Проверка сервера

Три команды, которые подтверждают, что бэкенд жив. Их стоит выполнить до
того, как браться за паяльник.

**Здоровье API и связь с брокером:**

```bash
curl https://monitor.example.com/api/health
# {"ok":true,"mqtt":true}
```

Поле `mqtt` показывает, подключён ли мост к брокеру. Если там `false`,
смотрите `logs api`, чаще всего дело в несовпавшем `MQTT_PASSWORD`.

**Вход в панель:**

```bash
curl -s -X POST https://monitor.example.com/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"ваш@email","password":"ваш_пароль"}'
# {"access_token":"eyJ...","token_type":"bearer"}
```

**Приём данных.** Самая полезная проверка: имитирует станцию и сразу
показывает, работает ли весь путь от брокера до базы. Подставьте свои
`MQTT_USER`, `MQTT_PASSWORD` и `DEVICE_ID`:

```bash
docker compose --profile prod exec mosquitto \
  mosquitto_pub -h localhost -u station -P ВАШ_MQTT_PASSWORD \
  -t env/station-01/status -r \
  -m '{"device_id":"station-01","online":true,"fw":"test","rev":0,
       "boot":"deadbeef","uptime_s":60,"status_interval_ms":30000,
       "sensors":{"bme":true,"sd":true}}'

docker compose --profile prod exec mosquitto \
  mosquitto_pub -h localhost -u station -P ВАШ_MQTT_PASSWORD \
  -t env/station-01/telemetry \
  -m '{"seq":1,"ts":0,"ts_valid":false,"up_ms":60000,"boot":"deadbeef",
       "temp":21.5,"hum":55,"pres":1012,"tds":380,"gps_valid":false}'
```

После этого станция должна появиться в панели как «На связи», а замер —
на графиках. Если не появилась, смотрите `logs api`: мост пишет туда и
про незарегистрированные `device_id`, и про невалидный JSON.

Посмотреть, что реально летает в брокере:

```bash
docker compose --profile prod exec mosquitto \
  mosquitto_sub -h localhost -u station -P ВАШ_MQTT_PASSWORD -t 'env/#' -v
```

Резервный путь по HTTP (`POST /api/v1/ingest` с заголовком
`X-Device-Token`) тоже работает, им удобно проверять сервер обычным
`curl`, пока брокер не настроен.

Полный список эндпоинтов лежит в Swagger:
`https://monitor.example.com/api/docs`.

## 6. Прошивка станции

Распиновка, ссылки на библиотеки и разбор ошибок компиляции описаны в
`firmware/INSTRUCTIONS.md`. Здесь только то, что касается связки с
сервером.

### Библиотеки

Через менеджер библиотек Arduino IDE ставятся ArduinoJson (только
версия 7 и выше, шестая не подойдёт), PubSubClient, Adafruit BME280 с
зависимостями, RTClib и TinyGPSPlus. Отдельными ZIP-архивами с GitHub
ставятся `iarduino_I2C_TDS` и `Battery_Shield`.

Для поддержки ESP32 добавьте в настройках IDE ссылку на менеджер плат:

```
https://espressif.github.io/arduino-esp32/package_esp32_index.json
```

Плата — `ESP32 Dev Module`.

### Правки в `firmware/config.h`

```c
#define DEVICE_ID     "station-01"          // как DEVICE_ID в .env сервера
#define WIFI_SSID     "ваша_сеть"
#define WIFI_PASSWORD "пароль_сети"
#define MQTT_SERVER   "monitor.example.com" // адрес сервера с брокером
#define MQTT_PORT     1883
#define MQTT_USER     "station"             // как MQTT_USER в .env
#define MQTT_PASSWORD "пароль_брокера"      // как MQTT_PASSWORD в .env
#define OTA_PASSWORD  "свой_пароль_для_обновления_по_воздуху"
```

Прошивка подключается обычным `WiFiClient` без шифрования, по порту
1883. Пароль при этом ходит по сети открытым текстом, так что для работы
через интернет нужен VPN между станцией и сервером, см. замечание в
разделе про файрвол.

### Заливка

Первый раз только по USB. Папка должна называться `firmware`, как и файл
`firmware.ino`, иначе IDE не откроет скетч.

Откройте монитор порта на скорости 115200. Если всё хорошо, увидите
примерно такое:

```
=== Станция мониторинга, fw 4.0.0 ===
[info] bme_ok: BME280 инициализирован
Инициализация завершена
WiFi OK, IP: 192.168.1.42
[info] mqtt_connected: Соединение с брокером установлено
{"seq":1,"ts":1757942400,"ts_valid":true,...}
```

Строка `MQTT ошибка, state=...` означает, что до брокера не дошли или
его не приняли. Коды: `-2` не удалось подключиться к адресу, `4` неверный
логин или пароль, `5` брокер отказал в авторизации.

Строки вида `*_fail` означают, что модуль не отозвался. Станция при этом
продолжит работать, а соответствующие поля уйдут как `null`. Подключить
модуль можно и позже, прошивка подхватит его сама в течение 30 секунд.

SD-карта: FAT32, до 32 ГБ, лучше свежеотформатированная. Папку `/spool`
прошивка создаст сама.

Когда станция окажется в сети, в IDE появится сетевой порт
`station-01 at <IP>`, и дальше можно обновлять по воздуху, вводя
`OTA_PASSWORD`.

## 7. Первый вход в панель

Откройте `https://monitor.example.com` и войдите под `ADMIN_EMAIL` и
`ADMIN_PASSWORD`.

Что сделать сразу:

1. Зайти в **Сводку** и убедиться, что станция помечена «На связи», а
   нужные датчики горят зелёным.
2. В **Настройках** выставить рабочий интервал замера. Заводские 60
   секунд удобны для отладки, но для долгой автономной работы обычно
   ставят 5–15 минут, это и ресурс батареи, и объём базы. После
   сохранения станция применит настройки при следующем обмене, а до тех
   пор панель будет честно показывать «Ожидает применения».
3. Завести операторам отдельные аккаунты вместо общего админского. Учтите,
   что в текущей версии права у всех аккаунтов одинаковые, разграничения
   нет.

Заодно стоит один раз проверить буферизацию, до того как станция уедет
на объект. Обесточьте роутер или унесите станцию из зоны Wi-Fi на
несколько минут. Статус сменится на «Нет связи», а когда станция
вернётся в сеть, поле «Буфер на SD» в сводке сначала покажет накопленные
файлы, а потом обнулится. Данные догрузятся пачками, дыры в графиках не
останется.

## 8. Время на станции

Этому разделу уделено столько места, потому что при первом запуске часы
почти наверняка окажутся сбитыми, а испорченные метки времени
обесценивают всю историю измерений.

Источников времени три:

| Источник | Когда используется | Точность |
|---|---|---|
| GPS | как только появился фикс со спутников | эталонная, сеть не нужна |
| Сервер | при первом успешном обмене | доли секунды |
| RTC (DS3231) | между перезагрузками | свой ход, со временем дрейфует |

Главное правило: RTC считается достоверным только после того, как его
выставил GPS или сервер. Проверки «год выглядит правдоподобно»
недостаточно. Севшая батарейка CR2032 оставляет в часах старое время,
которое такую проверку проходит, хотя на деле смещено на недели. Именно
поэтому при первом запуске время и оказывается сбитым.

GPS важнее серверного времени: он берётся со спутников и не зависит ни
от сети, ни от чужих часов. Если станция уже синхронизована по GPS,
серверное время её не трогает.

Пока часы не выставлены, станция ничего не выдумывает. Каждое измерение
уходит с `ts_valid: false` и полем `up_ms`, где лежит число миллисекунд
с момента загрузки. В статусе станция отдельно сообщает текущий аптайм и
идентификатор сеанса работы. Сервер по разнице восстанавливает момент
замера:

```
время замера = время приёма − (текущий аптайм − up_ms записи)
```

Это работает и для записей, пролежавших в буфере SD. Без такой
реконструкции все измерения, сделанные до первого фикса GPS, слиплись бы
в одну точку по времени приёма, и график превратился бы в вертикальную
черту.

Идентификатор сеанса нужен по двум причинам. Во-первых, он не даёт
применить `up_ms` от предыдущей загрузки, ведь после перезагрузки
счётчик начинается заново. Во-вторых, он служит ключом дедупликации для
таких записей: их вычисленное время при повторной отправке батча слегка
плывёт, а пара «сеанс и номер замера» остаётся неизменной.

В панели состояние часов видно в боковой панели: либо «Часы по GPS»
(или по серверу, или по RTC), либо «Часы не выставлены». Если вторая
надпись держится долго при живой связи, проверьте, доходят ли до станции
ответы сервера.

Если GPS недоступен постоянно, например станция стоит в помещении, время
всё равно будет верным, его выставит сервер при первом обмене. GPS тогда
нужен только для координат.

Проверить всё это на живой станции можно так: выньте батарейку из DS3231
на минуту, включите станцию без антенны GPS и смотрите монитор порта.
Сначала появится `rtc_lost_power`, затем, после первого успешного
обмена, `time_set` с источником `server`. Замеры, сделанные в промежутке,
попадут в график с правильными интервалами, а не одной точкой.

## 9. Локальная разработка

На своей машине, без сервера:

```bash
cp .env.example .env
docker compose --profile dev up --build
```

Секреты в dev можно любые, наружу ничего не смотрит.

| Что | Где |
|---|---|
| Панель с горячей перезагрузкой | http://localhost:5173 |
| API с автоперезапуском | http://localhost:8000/api/docs |
| PostgreSQL для psql или DBeaver | `localhost:5432` |

Исходники смонтированы томами, поэтому правки в `backend/app` и
`frontend/src` подхватываются без пересборки. Caddy в этом профиле не
участвует, `/api` проксирует сам Vite.

## 10. Обслуживание

### Обновление кода

Замените файлы проекта и пересоберите:

```bash
cd /opt/envmon
docker compose --profile prod up -d --build
```

Простой измеряется секундами, пока перезапускается `api`. Станция этого
не заметит: неотправленное измерение уйдёт на SD и догрузится следующим
запросом.

### Бэкап базы

```bash
docker compose --profile prod exec -T db \
  pg_dump -U envmon envmon | gzip > backup-$(date +%F).sql.gz
```

То же самое в cron, раз в сутки:

```
0 3 * * * cd /opt/envmon && docker compose --profile prod exec -T db pg_dump -U envmon envmon | gzip > /var/backups/envmon-$(date +\%F).sql.gz
```

Восстановление:

```bash
gunzip -c backup-2026-09-15.sql.gz | \
  docker compose --profile prod exec -T db psql -U envmon envmon
```

Файл `.env` тоже забэкапьте, причём отдельно от дампов. Без `JWT_SECRET`
и `DEVICE_TOKEN` восстановленная база бесполезна.

### Логи

```bash
docker compose --profile prod logs -f api
docker compose --profile prod logs -f caddy
```

Журнал самой станции, то есть ошибки датчиков, обрывы связи и действия
операторов, смотрите в панели, в разделе «Журнал». Там же видно, кто
именно менял настройки.

### Прямой доступ к базе

```bash
docker compose --profile prod exec db psql -U envmon envmon
```

Удалить тестовое измерение из пятого раздела:

```sql
DELETE FROM measurements WHERE seq = 1 AND device_id = 'station-01';
```

Посмотреть объём таблиц:

```sql
SELECT relname, pg_size_pretty(pg_total_relation_size(relid))
FROM pg_catalog.pg_statio_user_tables ORDER BY pg_total_relation_size(relid) DESC;
```

### Смена пароля брокера

Поменяйте `MQTT_PASSWORD` в `.env` и перезапустите брокер вместе с API:

```bash
docker compose --profile prod up -d mosquitto api
```

Файл паролей пересоздаётся при старте контейнера. Дальше перепрошейте
станцию с тем же значением. Пока пароли не совпадают, станция не
подключается и пишет данные на SD, так что потерь не будет, всё
выгрузится после починки.

### Смена токена резервного HTTP-приёма

Поменяйте `DEVICE_TOKEN` в `.env` и перезапустите `api`. Новый хеш
перезапишется в базе автоматически.

### Добавление второй станции

Сервер рассчитан на несколько станций: модели, API и приём данных
работают с произвольным числом устройств. Панель в текущей версии
показывает первое устройство из списка. Чтобы завести вторую станцию,
добавьте запись в таблицу `devices` с её `device_id` и SHA-256 от
токена, а в интерфейсе понадобится доработать переключатель станций.

## 11. Разбор проблем

### Compose не стартует

Сообщение вида `задайте POSTGRES_PASSWORD в .env` означает, что
обязательная переменная пуста. Заполните и повторите.

Если ругается на `profiles`, у вас compose первой версии. Поставьте
плагин v2 и вызывайте `docker compose`, без дефиса.

### Контейнеры поднялись, но панель не открывается

Скорее всего Caddy не выпустил сертификат, смотрите `logs caddy`.
Типичные причины: домен не указывает на сервер, 80-й порт закрыт
файрволом или занят другим веб-сервером (проверьте
`ss -tlnp | grep :80`). Let's Encrypt проверяет владение доменом именно
через 80-й порт, даже если вам нужен только 443-й.

Если вместо панели белый экран без ошибок, откройте консоль браузера.
Когда запросы к `/api/*` уходят не туда, дело в `Caddyfile`: блок
`handle /api/*` должен идти до общего `handle`.

### API отвечает, но данных нет

Контейнер `api`, который перезапускается по кругу, почти всегда упирается
в базу. В `logs api` будет сообщение о недоступности PostgreSQL, а
причину покажет `logs db`. Чаще всего это несовпадение пароля с уже
существующим томом `pgdata`: пароль из `.env` применяется только при
первой инициализации тома. Если меняли его позже, либо верните старый,
либо смените пароль внутри самой базы через `psql`.

### Станция не появляется в панели

По порядку, от простого к сложному:

1. Есть ли в мониторе порта строка `WiFi OK` с IP? Если нет, проблема в
   сети, а не в сервере.
2. Есть ли `mqtt_connected`? Если вместо неё `MQTT ошибка, state=-2`,
   станция не достучалась до брокера: проверьте `MQTT_SERVER` в
   `config.h` и открытый порт 1883 на сервере.
3. `state=4` или `state=5` означают, что не совпали `MQTT_USER` и
   `MQTT_PASSWORD` с тем, что записано в `.env` сервера.
4. Станция подключилась, но в панели пусто? Почти наверняка расходится
   `DEVICE_ID`. В `logs api` будет строка «Сообщение от
   незарегистрированной станции».

### Данные копятся на SD и не уходят

Посмотрите «Буфер на SD» в сводке. Если число файлов растёт, сервер не
принимает сообщения, разбирайтесь по предыдущему пункту. Данные при этом
не теряются: курсор очереди двигается только после успешной отправки, и
после починки всё догрузится.

### Показания странные

**EC на три порядка меньше ожидаемого** (`0.8` вместо `800`). В
библиотеке `iarduino_I2C_TDS`, начиная с версии 1.3.0, `getEC()`
возвращает мСм/см, а сервер ждёт мкСм/см. Поставьте `tds_scale = 1000` в
настройках станции либо поправьте пороги `ec` в
`backend/app/analysis.py`.

**TDS явно врёт.** Модуль требует калибровки по двум растворам, 500 и
1500 ppm, процедура описана в вики производителя. Поля `tds_offset` и
`tds_scale` в панели дают мягкую поправку, но нормальную калибровку не
заменяют.

**Температура завышена на 1–2 °C.** Обычное дело для BME280 рядом с
греющимся ESP32. Разнесите модули или скомпенсируйте через `temp_offset`.

**Локации называются «Точка 52.518, 5.471».** Значит, обратное
геокодирование недоступно: нет интернета или выставлено
`GEOCODE_ENABLED=false`. На данные это не влияет, имя можно поправить
вручную в разделе «Локации».

**Ошибки компиляции прошивки** разобраны отдельно в
`firmware/INSTRUCTIONS.md`, включая конфликт версий библиотек iarduino и
переключатель `USE_BATTERY_SHIELD` для сборки без модуля питания.

## Памятка: что должно совпадать

Рассогласование этих значений даёт большинство проблем при первом
запуске:

| `.env` сервера | `firmware/config.h` |
|---|---|
| `DEVICE_ID` | `DEVICE_ID` |
| `MQTT_USER` | `MQTT_USER` |
| `MQTT_PASSWORD` | `MQTT_PASSWORD` |
| адрес сервера из `SITE_ADDRESS` | `MQTT_SERVER` |

Отдельно стоит `DEVICE_TOKEN`: он есть только в `.env` и нужен
резервному HTTP-приёму, в прошивке его нет.
